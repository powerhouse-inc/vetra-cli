# ED.00 Check the prerequisites for creating a document editor

For this scenario, you will write TypeScript code in the active Reactor Package project directory that
you can locate with `{{commands.reactor-project-ls.id}}`.
- Use `{{commands.reactor-project-start.id}}` / `{{commands.reactor-project-restart.id}}` to (re)start
  Vetra Studio and Vetra Switchboard if needed.
- Use `{{commands.reactor-project-logs.id}}` to inspect the logs.

Read the `AGENTS.md` in the project directory for best practices.

For **spec** documents (document model + editor specs), use the `spec-*` commands. Specs live as files
under `<project>/specs/`.

For **preview / test documents** in the running reactor, use the `{{services.reactor-project.mcpPrefix}}*`
MCP tools — these talk to the Preview Drive in the running Vetra Switchboard.

Do not run `ph vetra` or `ph generate` manually. Use `{{commands.reactor-project-start.id}}` /
`{{commands.reactor-project-restart.id}}` to keep the watcher alive, and `{{commands.spec-generate.id}}`
to regenerate code from a spec.

Code is regenerated automatically by the Vetra watcher when the spec file changes.
- Review bugs and errors in the GraphQL types if the code generator is stuck.
- Use `{{commands.spec-update.id}}` to fix type errors, then `{{commands.spec-generate.id}}` to force a
  regen if needed.
- Consider restarting the project with `{{commands.reactor-project-restart.id}}` if the watcher is wedged.

## ED.00.1 Familiarize yourself with the document model

- Use `{{commands.spec-get.id}} --project <name> --name "<Model Name>" --latest` to read the document
  model spec.
- In `<project>/src/document-models/<model>/`, confirm you see the types and code for reducers and
  explore their functionality.
- Run `pnpm test` (inside the project) to verify all tests are passing.
- Run `pnpm build` to detect type errors.

Fix any issues you may detect.

## ED.00.2 Ensure the editor spec exists

- Use `{{commands.spec-list.id}} --project <name> --type powerhouse/document-editor` to confirm whether a
  preliminary editor spec already exists for the target document model.
- If it exists, note the document ID for the task outcome.
- If it does not exist, create it now:

  ```
  spec-create --project <name> --type powerhouse/document-editor --name "<Editor Name>"
  ```

  - **NEVER** set the document ID manually; `spec-create` auto-generates the header.
  - Use a descriptive `--name` (e.g. `Pizza Plaza Order Editor`); the on-disk filename is derived from it.
  - Confirm the spec is listed by re-running `spec-list`.

## ED.00.3 Confirm the document type and editor name

- Look up the available actions FIRST with
  `{{commands.spec-schema.id}} --type powerhouse/document-editor`, then use the
  literal action names it returns. Do not assume the names below are correct
  for any other doc type — each doc-type has its own action vocabulary.
- For `powerhouse/document-editor` specifically, you need to apply (in order):
  - Register the target document type on the editor (action `ADD_DOCUMENT_TYPE`).
  - Set the editor name as it will appear in the codebase (action `SET_EDITOR_NAME`).
  - Confirm with status `"CONFIRMED"` (action `SET_EDITOR_STATUS`).

  Batch all three into a single `spec-update --actions '[...]'` call where possible.

- Verify with `{{commands.spec-get.id}} --project <name> --name "<Editor Name>" --filter $.global`.

## ED.00.4 Verify code generation and the editor boilerplate

- Run `{{commands.spec-generate.id}} --project <name> --name "<Editor Name>"` (or wait for the watcher
  to pick up the spec change).
- Verify the editor boilerplate was created under `<project>/editors/<editor-name>/`.
- Explore the boilerplate code, which you can recognize by the usage of the `<DocumentStateViewer>`
  component.
