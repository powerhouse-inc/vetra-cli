Designing a Powerhouse document model = editing a `.phdm.phd` spec file
through `spec-*` tools, then running `spec-generate`. Specs under
`<project>/specs/` are the source of truth; the generated code under
`document-models/` is not.

## Required reading (do not skip)

- **Before any `spec-update` call**, `skill_read` the spec-update
  cheatsheet reference. It documents action types (`SET_INITIAL_STATE`,
  `ADD_MODULE`, `ADD_OPERATION`, `SET_OPERATION_REDUCER`, …), required
  input fields (`moduleId`, `scope`, `initialValue`), and the
  SCREAMING_SNAKE naming rule. The tool errors echo input schemas but
  not *which* action to pick — that lives here.
- **Before writing a reducer**, `skill_read` `03.implement-reducers`.
  Reducers are authored as TypeScript in
  `<project>/document-models/<model>/v1/src/reducers/<module>.ts`,
  using `mastra_workspace_edit_file` (or `mastra_workspace_write_file`
  for a fresh file). The spec carries only the operation **schema**;
  `spec-generate` lays down the reducer method skeleton, you fill the
  body. **`SET_OPERATION_REDUCER` is rejected by `spec-update`** and
  `ADD_OPERATION` is rejected when it carries a `reducer` field — both
  point at the file path to edit. Treat the rejection as the canonical
  signal to switch to the workspace edit tool.
  The state argument is the **global slice** (e.g. `state.workouts`),
  NOT the full `PHState` (`state.global.workouts` is wrong). Check the
  signature in `<v1>/gen/<module>/operations.ts`.

## Workflow gates

1. **State schema** in GraphQL SDL, applied via `SET_STATE_SCHEMA`. Model
   file/image/attachment fields as a content-addressed ref in a `String`
   (`attachment://v1:<hash>`) — see DM.02 "Images and attachments"; not a
   `URL`, not the `Attachment` scalar.
2. **Initial state** as a JSON string, applied via `SET_INITIAL_STATE`
   with `scope: "global"` and `initialValue`.
3. **Modules** (`ADD_MODULE`) before operations.
4. **Operations** (`ADD_OPERATION`) with `moduleId`, SCREAMING_SNAKE
   `id` and `name`, input schema in GraphQL SDL. Omit `reducer` — the
   body comes later via the workspace write tool, not via the spec.
5. **`spec-generate`** until clean. Produces editable reducer
   skeletons under `<project>/document-models/<model>/v1/src/reducers/`.
   Tsc/eslint errors at this stage are spec problems; fix the spec, not
   the generated output.
6. **Reducer bodies** — write them with `mastra_workspace_edit_file`
   into `<v1>/src/reducers/<module>.ts`. Save tests in
   `<v1>/tests/<module>.test.ts` and run `pnpm test` from the project.

If `spec-generate` reports type errors that originate in a reducer
`.ts` file (not the spec), edit the reducer with
`mastra_workspace_edit_file`. `SET_OPERATION_REDUCER` will reject —
reducer source is authored under `<v1>/src/reducers/`, not specified.

## Never

- Hand-edit files under `<v1>/gen/` — those are regenerated and
  clobbered on every `spec-generate`. The `<v1>/src/reducers/` and
  `<v1>/tests/` siblings ARE editable; that's where reducer code lives.
- Restart the reactor after a spec change or reducer edit. The watcher
  + Vite HMR pick it up. Only restart if `reactor-project-logs` shows a
  missed edit.
