# DM.04 spec-update input reference (cookbook)

Load this when you are about to compose a `spec-update` and want the exact
action input shapes, or when a `spec-update` / `spec-generate` failed on a
shape or schema-language error. Each action's authoritative input shape
comes from `{{commands.spec-schema.id}} --type <doc-type> --action <ACTION>` —
run that when unsure rather than guessing; the shapes below are taken
verbatim from those schemas.

## Worked example: building a document model

A representative batched `spec-update` for a todo-list model:

    spec-update --name "Todo List" --actions '[
      { "type": "SET_STATE_SCHEMA", "input": {
          "scope": "global",
          "schema": "type TodoItem {\n  id: ID!\n  text: String!\n  completed: Boolean!\n}\n\ntype TodoListState {\n  items: [TodoItem!]!\n}"
      }},
      { "type": "SET_INITIAL_STATE", "input": {
          "scope": "global",
          "initialValue": "{ \"items\": [] }"
      }},
      { "type": "ADD_MODULE", "input": {
          "id": "todos",
          "name": "todos"
      }},
      { "type": "ADD_OPERATION", "input": {
          "moduleId": "todos",
          "id": "ADD_TODO",
          "name": "ADD_TODO",
          "schema": "input AddTodoInput {\n  id: ID!\n  text: String!\n}",
          "reducer": "state.items.push({ id: action.input.id, text: action.input.text, completed: false });"
      }}
    ]'

What the shapes mean:

- `scope` is `"global"` (the only scope unless you are explicitly writing
  `local` state).
- `ADD_MODULE` takes `id` + `name` — there is no `moduleName` shortcut.
- `ADD_OPERATION` references its parent module by `moduleId` (= the
  module's `id`); its own `id` / `name` are the literal action `type`,
  which must be SCREAMING_SNAKE_CASE (`^[A-Z][A-Z0-9_]*$`) — `ADD_TODO`,
  not `"Add Todo"` or `addTodo`. The reducer throws a `Did you mean "..."?`
  hint if it isn't.
- The reducer can be set inline via `ADD_OPERATION.reducer`, or later with
  `SET_OPERATION_REDUCER` (input `{ id, reducer }`, where `id` is the
  operation's id).

## Schema fields are GraphQL SDL, not TypeScript

`SET_STATE_SCHEMA.schema` and `ADD_OPERATION.schema` are **GraphQL SDL**.
The TypeScript form passes JSON validation but fails `spec-generate` with a
GraphQL parse error — so write:

    type TodoItem { id: ID!  text: String!  completed: Boolean! }

not:

    type TodoItem = { id: string; text: string; completed: boolean; }

## Other document-model gotchas

- Action `type` values are LITERAL strings defined per doc-type. Never
  invent them, never strip a prefix, never extrapolate by pattern. For
  example `powerhouse/subgraph` uses `SET_SUBGRAPH_NAME` /
  `SET_SUBGRAPH_STATUS` — not `SET_NAME` / `SET_STATUS`.
- A freshly created `powerhouse/document-model` spec already contains v1 in
  its `specifications` array. All edits (state schema, modules, operations,
  reducers) apply to the latest version automatically — do **not** call
  `RELEASE_NEW_VERSION` to "start working." That action seals the current
  spec and opens an empty v(n+1), which leaves your v1 generated code as a
  broken stub. Only call `RELEASE_NEW_VERSION` once v1 is stable and you
  want to begin a backwards-incompatible v2.
- Before composing any `spec-update`, fetch the canonical names with
  `spec-schema --type <doc-type> --filter "$.specifications[(@.length-1)].modules[*].operations[*].name"`.
- Batch multiple actions into a single `spec-update` call where possible.
