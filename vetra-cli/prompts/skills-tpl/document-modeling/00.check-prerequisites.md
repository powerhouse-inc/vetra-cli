# DM.00 Check the prerequisites for creating a document model

Note on task management:
- The creation of a new document model is associated with a single goal/task in your WBS document.
- Add notes to remember your progress and update the goal status in your WBS document as you go along.

## DM.00.1 Ensure you have the required input and context

- Ensure you know who the stakeholder is who is requesting the new document model.
- Ensure you can contact the stakeholder through your inbox to ask questions and share updates.
- Ensure you have identified the WBS goal associated with the task. Create a new goal if needed.
- Rephrase the stakeholder request for clarity if needed.
- Ensure you know at least the informal name of the new document model and who the users are.
- Ensure that you know which Reactor Package project this document model will be in. The project is a
  sub-folder of the current workdir; pass its name as `--project <name>` to every `spec-*` command,
  or `cd` into it.

## DM.00.2 Locate the target project and start the reactor service

- Use `{{commands.reactor-project-ls.id}}` to list the available Reactor Package projects under the workdir.
- Confirm the target project is in the list. If it doesn't exist yet, create it with
  `{{commands.reactor-project-init.id}}`.
- Check which projects are running with `{{commands.reactor-project-ps.id}}`. If a different project is
  running, stop it first with `{{commands.reactor-project-stop.id}}`.
- Start the target project with `{{commands.reactor-project-start.id}}` if it's not already running.
- Once the project is running, confirm the `{{services.reactor-project.mcpPrefix}}*` MCP tools are
  available — they target the Preview Drive in the running reactor where you'll create test documents
  later. **Spec documents themselves live as files on disk under `<project>/specs/`; you read and edit
  them with `spec-*` commands, not with MCP tools.**

## DM.00.3 Review existing specs and package implementation

- Use `{{commands.spec-list.id}} --project <name>` to inspect every spec already in the project (document
  models, editors, processors, subgraphs, apps).
- For each relevant spec, use `{{commands.spec-get.id}} --project <name> --name <spec-name>` to read
  the current contents and consider how the new document model fits in.
- Review the package implementation under `<project>/src/` (document-models, editors, etc.) and confirm
  unit tests pass with `pnpm test` from inside the project.
- Make sure there are no uncommitted changes. Commit outstanding changes if needed.

## DM.00.4 Ensure the Reactor Package information is sufficiently updated

- Use `{{commands.spec-list.id}} --project <name> --type powerhouse/package` to check whether a package
  spec already exists.
- If it does not exist yet, create one with
  `{{commands.spec-create.id}} --project <name> --type powerhouse/package --name "<Package Name>"`
  before proceeding with the new document model.
- Consider the expanded scope with the new document model. Think about whether the package name,
  description, category, publisher + URL and keywords would benefit from an update.
- Decide whether it's worth updating:
  - If you just created the package spec, fill it in with `{{commands.spec-update.id}}`.
  - If the package spec already exists, don't update it lightly. If you do decide to update it, confirm
    with the stakeholder first.

### Expected Task Outcome

The Reactor Package information reflects the expanded scope, and the running project's MCP endpoints are
available for the next steps.

## DM.00.5 Provide a stakeholder update

- Use `{{commands.reactor-project-ps.id}}` to surface the Vetra Studio, Vetra Switchboard and MCP
  endpoints of the running project.
- Notify the stakeholder that you started the document modeling task and summarize your task for them
  based on your considerations to this point.
- Share the endpoints so they can follow along.

## Expected Scenario Outcome

All prerequisites are in place for the agent to start writing the document model description.
