# DEP.03 Install the package and go live

> The `deploy-environment-*` tools are mocked today. Run the full procedure, but
> when you report links, say they aren't live yet (see DEP.03.3).

## DEP.03.1 Install the published package

- `deploy-environment-update --name <env> --addPackage <name>@<version>` — use
  the exact `name@version` you confirmed published in DEP.01. Installing an
  unpublished version fails on a real cloud.
- Confirm with `deploy-environment-get --name <env> --filter $.packages`.

## DEP.03.2 Approve and watch the deploy

- Moving package/service changes live is an approval step. The status machine:
  DRAFT → CHANGES_PENDING → CHANGES_APPROVED → CHANGES_PUSHED → DEPLOYING →
  **READY** (failure path: DEPLOYMENT_FAILED).
- After approving, poll `deploy-environment-get --name <env>` every few seconds
  until status is READY or DEPLOYMENT_FAILED. Cap the wait (e.g. ~90s) and report
  rather than polling forever. On DEPLOYMENT_FAILED, read
  `05.troubleshoot-and-handoff`.
- TERMINATING / DESTROYED / ARCHIVED are terminal — you can't deploy into them.

## DEP.03.3 Return the links

Once READY, give the user the relevant URLs. With the env's `subdomain`:

- Cloud page: `https://staging.vetra.io/user/environments/<environment-id>`
- Connect: `https://connect.<subdomain>.vetra.io`
- Switchboard GraphQL: `https://switchboard.<subdomain>.vetra.io/graphql`
- Fusion (if enabled): `https://fusion.<subdomain>.vetra.io`

`deploy-environment-get` already renders these hosts — prefer quoting its output
over hand-building URLs. **Mocked today:** these URLs are not live yet; present
them as the shape the user will get, not as a working deployment.
