# DEP.00 Preflight and package identity

## DEP.00.0 Authorize

`whoami`. Not authorized → follow the skill's **Authentication** section (user
clicks **Authorize agent** in the Studio top bar) before any environment step.

## DEP.00.1 Type-check

Run `reactor-project-check` (`--name <project>` when the workdir isn't the
project). Fix every error first — a broken build wastes a publish and an env
slot. Errors in a document model or editor are a handoff signal, not a fix from
here (`05.troubleshoot-and-handoff`).

## DEP.00.2 Identify the package

Read `<project>/package.json` `name` and `version`. This `name@version` is what
you publish and then install — the two must match, or the env runs a different
build than you shipped. No `name` → not publishable; stop and tell the user.

## DEP.00.3 Target environment

Pin a target **only if the user named one** (name/subdomain) or asked for a new
one. Otherwise don't assume — you resolve it in `02.environment` by listing and
asking. Never pick or create on the user's behalf.

## DEP.00.4 Is a deploy needed? (skip when already up to date)

A deploy only matters when it changes what runs in the target. With a clear
target (named env, or exactly one), settle this with two **read-only** checks
before building or publishing:

1. `reactor-project-publish-status --registry <env registry>` (the env's
   `defaultPackageRegistry`; see `02.environment`) — unpublished source changes,
   or is the current `name@version` already the latest published?
2. `deploy-environment-list`, then `deploy-environment-get --name <env> --filter
   $.packages` — is this package installed there, and at which version?

- **Not installed** → deploy (first install).
- **Installed, but** there are unpublished changes **or** the installed version
  is older than the latest published → deploy (publish and/or update the env).
- **Installed at the current published version, no unpublished changes** →
  **nothing to deploy.** Say it's already live, return the links (DEP.03.3), and
  stop — no build, no publish, no "should I deploy?".

Several envs and none named → you can't pin a target: list them in
`02.environment`, annotate each with its state (up to date / update available /
not deployed), and let the user choose. Still don't propose one already up to
date.
