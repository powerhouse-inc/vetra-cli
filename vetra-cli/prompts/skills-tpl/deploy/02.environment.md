# DEP.02 Reuse or create the environment

> `deploy-environment-list` / `-get` are live and read the user's real
> environments (you must be authorized — see the skill's **Authentication**
> section; check with `whoami`). `deploy-environment-create` / `-update` are
> still mocked: drive them as the real procedure, but don't report their results
> as live state.

## DEP.02.1 Reuse before creating

- Run `deploy-environment-list` and look for one matching the user's intent (by
  name or subdomain). Reuse it — a duplicate environment fragments the user's
  deployments.
- Inspect a candidate with `deploy-environment-get --name <id|name|subdomain>`
  to see its status, services, installed packages, and `defaultPackageRegistry`.

## DEP.02.2 Create only when none fits

- `deploy-environment-create --name "<label>"` mints a new environment:
  auto-assigns a `<subdomain>.vetra.io` host, starts in DRAFT with CONNECT
  enabled.
- Its `defaultPackageRegistry` is where it installs packages from. Publish to
  that same registry (DEP.01) so the install can resolve your package.

## DEP.02.3 Enable the services the app needs

- `deploy-environment-update --name <env> --enableService CONNECT,SWITCHBOARD`
  (add `FUSION` if the app uses it). Enable only what the app needs; disable with
  `--disableService`.
