# DEP.02 Choose the target environment (always ask)

> `deploy-environment-*` is live and acts on the user's real environments
> (authorize first — `whoami`, skill **Authentication**).

**Never deploy into, or create, an environment the user hasn't explicitly
chosen.** The wrong target is too costly to undo — the user picks, not you.

## DEP.02.1 List and ask

- `deploy-environment-list` first, every time — even when the user named an env,
  confirm it appears here.
- Present each (name, subdomain, status) and ask which to deploy to, or whether
  to create a new one. Stop and wait for the answer.
  - User already named a specific env → that's their choice; confirm it's listed
    and proceed, don't re-ask.
  - Ambiguous, nothing matches, or empty list → ask. No "close enough" match, no
    silent create.
- Inspect the chosen env: `deploy-environment-get --name <id|name|subdomain>` →
  status, services, packages, `defaultPackageRegistry`.
- Skip any env with `isStudio: true` as a deploy target — it hosts the Studio
  itself and can't take a package deploy (DEP.02.5).
- Apply DEP.00.4 to it: already at the current version with no unpublished
  changes → nothing to deploy, return links (DEP.03.3) and stop. When presenting
  the list, annotate each env with that state so the user picks informed.

## DEP.02.2 Create only when the user asks

After the user picks "create" (or the list is empty and they confirm the first):
`deploy-environment-create --name "<label>"` mints one — auto-assigns a
`<subdomain>.vetra.io` host, starts DRAFT with CONNECT enabled. Publish (DEP.01)
to its `defaultPackageRegistry` so the install resolves.

## DEP.02.3 Reuse, don't duplicate

Point at an existing env when the user names one — a near-duplicate fragments
their deployments. If a "create new" request overlaps an env already listed,
flag it and let the user confirm.

## DEP.02.4 Enable services

Connect is required — the deployed app is served through it. Make sure `CONNECT`
is enabled on the target: a freshly created env already has it (DEP.02.2); for an
existing env, check `deploy-environment-get` services and add it if missing —
`deploy-environment-update --name <env> --enableService CONNECT`.

Switchboard and Fusion are opt-in — enable or disable them **only when the user
asks**, and support either direction:

- `deploy-environment-update --name <env> --enableService SWITCHBOARD,FUSION`
- `deploy-environment-update --name <env> --disableService FUSION`

Don't toggle a service the user didn't mention, and don't disable `CONNECT` — the
deploy needs it.

## DEP.02.5 Vetra Studio environments are off-limits

Some of the user's environments **run Vetra Studio itself** —
`deploy-environment-list` returns them with `isStudio: true` (or confirm via the
`vetra` package in `deploy-environment-get --filter $.packages`).

- **Never pick a Studio environment as a deploy target.** Installing a project
  package there corrupts the Studio host. The tools enforce this:
  `deploy-environment-update --addPackage` against a Studio env is rejected, so
  don't try to force it through.
- If the user names their Studio env, or the only environments are Studio envs,
  don't deploy there — explain why and create a separate deploy env (DEP.02.2).
