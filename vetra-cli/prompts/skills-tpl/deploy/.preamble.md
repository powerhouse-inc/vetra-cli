Deploying a Vetra project means taking a built Reactor package and making it
run in a cloud environment: **build → publish → reuse/create an environment →
install the package → return the live links**. You drive this with the
`reactor-project-*` and `deploy-environment-*` tools.

**Current reality — read before you promise anything.** The environment tools
(`deploy-environment-create`, `-list`, `-get`, `-update`) return **mocked data**
today; cloud auth isn't wired up yet. Build, publish, and the registry check
(`reactor-project-publish-status`) are real. So you can genuinely build and
publish a package, but you must **not** tell the user an environment is live or
hand them a working URL until the env tools are backed by the real cloud. State
plainly when a step is simulated.

## Required reading

- **Before deciding whether to publish**, `skill_read` `01.build-and-publish`.
  It defines the publish-if-changed rule and how to read
  `reactor-project-publish-status`.
- **Before any environment step**, `skill_read` `02.environment` (reuse vs
  create) and `03.install-and-go-live` (status state machine + link shapes).
- **When the user asks a status question** ("is it published / installed /
  ready?") instead of asking for a deploy, go straight to
  `04.answer-status-questions`.
- **On any failure** (build error, publish/auth error, DEPLOYMENT_FAILED),
  `skill_read` `05.troubleshoot-and-handoff` before retrying — it decides when
  to fix locally vs hand off to the document-model / editor / app subagent.

## Workflow gates

A full deploy runs 00 → 03 in order; don't skip a gate.

1. **Preflight** (`00.preflight-and-identity`) — the project type-checks and you
   know the package `name@version`.
2. **Build & publish** (`01.build-and-publish`) — built, and the target version
   is in the registry (publish only if changed).
3. **Environment** (`02.environment`) — an environment exists with the right
   services enabled (reuse before creating).
4. **Install & go live** (`03.install-and-go-live`) — package installed, deploy
   approved, status polled to READY, links returned.

## Never

- Claim an environment is live, or present a URL as working, while the
  `deploy-environment-*` tools are mocked. Say it's simulated.
- Republish a version that `reactor-project-publish-status` already reports as
  published — bump the version first.
- Hand-edit generated code under `gen/` to force a deploy through.
