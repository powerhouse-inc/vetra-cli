Deploying a Vetra project takes a built Reactor package and makes it run in a
cloud environment: **build → publish → pick an environment (the user chooses) →
install → wait for READY → return links.** Drive it with two live tool families
— `reactor-project-*` (build/publish against a registry) and
`deploy-environment-*` (the user's real Vetra Cloud envs on staging.vetra.io) —
plus `whoami` for auth. Env writes, publishes, and the registry check are all
real; only call an environment live once `deploy-environment-wait` reports READY.

## Authentication (Renown)

Every `deploy-environment-*` call and every publish needs the user's Renown
identity connected to you. `whoami` is your only auth tool — it reports whether
you're authorized and as which address. **You cannot sign in yourself.**

Not authorized → tell the user to click **Authorize agent** in the Vetra Studio
top bar (next to "Auto-follow agent") and approve with Renown in their wallet —
not a terminal command, not a pasted URL. End your turn; when they confirm, call
`whoami` to verify, then retry their original request.

## The flow — run the gates in order, don't skip one

**First: is a deploy even needed?** For an unchanged project already installed at
the current version, it isn't. With a clear target (user named an env, or there's
exactly one), run two read-only checks — `reactor-project-publish-status` and
`deploy-environment-get --filter $.packages` — and if it's installed at the
current published version with no unpublished changes, say it's already live,
return the links (DEP.03.3), and **stop**: no build, no publish, no "should I
deploy?". Exact rule in `00.preflight-and-identity` DEP.00.4.

When a deploy is needed, `skill_read` each gate before acting on it:

1. **`00.preflight-and-identity`** — authorize, type-check, read the package
   `name@version`, confirm the deploy is needed (DEP.00.4).
2. **`01.build-and-publish`** — build, then publish *only if changed*; confirm
   the version is in the registry.
3. **`02.environment`** — list the envs, let the user pick the target (or approve
   creating one); ensure Connect is enabled, toggling other services only when
   the user asks. Never auto-pick or auto-create.
4. **`03.install-and-go-live`** — install, approve, wait to READY, return links.

Side-paths: a **status question** ("is it published / installed / ready?")
instead of a deploy → `04.answer-status-questions`. **Any failure** (build,
publish/auth, DEPLOYMENT_FAILED) → `05.troubleshoot-and-handoff` before retrying.

## Never

- Build, publish, or propose a deploy when the target (or only) env already runs
  the current published version with no unpublished changes — report it's up to
  date, with links (DEP.00.4).
- Deploy into or create an env the user didn't explicitly choose. Always
  `deploy-environment-list` and let them pick (or approve a new one) — no "close
  enough" match, no silent create.
- Deploy, publish, or install a project package into a **Vetra Studio
  environment** (one with the `vetra-cli` package installed). Those host the
  Studio itself; `deploy-environment-list` flags them `isStudio: true` and the
  tools reject the install. Use a separate env, or create one (DEP.02.5).
- Hide Vetra Studio environments when the user asks what environments they have
  or which are available. They're still the user's environments — list **every**
  one `deploy-environment-list` returns (note which are `isStudio: true` Studio
  hosts). Excluding them applies only to choosing a deploy target (DEP.02.5).
- Call an env live, or present a URL as working, before `deploy-environment-wait`
  reports READY.
- Republish a version `reactor-project-publish-status` already reports published
  — bump first.
- Hand-edit generated `gen/` code to force a deploy through.
