# DA.00 Check the prerequisites for creating a drive app

For this scenario, you will write TypeScript code in the active Reactor Package project directory that
you can locate with `{{commands.reactor-project-ls.id}}`.
- Use `{{commands.reactor-project-start.id}}` / `{{commands.reactor-project-restart.id}}` to (re)start
  Vetra Studio and Vetra Switchboard if needed.
- Use `{{commands.reactor-project-logs.id}}` to inspect the logs.

Read the `AGENTS.md` in the project directory for best practices.

For **spec** documents (document model + editor + app specs), use the `spec-*` commands. Specs live as
files under `<project>/specs/`.

For **preview / test documents** in the running reactor, use the `{{services.reactor-project.mcpPrefix}}*`
MCP tools — these talk to the Preview Drive in the running Vetra Switchboard.

Do not run `ph vetra` or `ph generate` manually. Use `{{commands.reactor-project-start.id}}` /
`{{commands.reactor-project-restart.id}}` to keep the watcher alive, and `{{commands.spec-generate.id}}`
to regenerate code from a spec.

Code is regenerated automatically by the Vetra watcher when the spec file changes.
- Review bugs and errors in the GraphQL types if the code generator is stuck.
- Use `{{commands.spec-update.id}}` to fix type errors, then `{{commands.spec-generate.id}}` to force a
  regen if needed.
- Do not restart the reactor after editing source files — Vite HMR + the
  spec watcher pick up changes automatically. Only call
  `{{commands.reactor-project-restart.id}}` if `{{commands.reactor-project-logs.id}}`
  shows the watcher missed an edit (no rebuild after the change).

## DA.00.1 Familiarize yourself with the document models the app will surface

- Use `{{commands.spec-list.id}} --project <name>` to see what document models exist.
- For each document type the app should surface, confirm the model spec exists and has an editor.
- If a document model or its editor doesn't exist yet, create them first using the
  `document-modeling` and `document-editor-creation` skills before building the app.

## DA.00.2 Ensure the app spec exists

- Use `{{commands.spec-list.id}} --project <name> --type powerhouse/app` to confirm whether an
  app spec already exists.
- If it does not exist, create it now:

  ```
  spec-create --project <name> --type powerhouse/app --name "<App Name>"
  ```

  - **NEVER** set the document ID manually; `spec-create` auto-generates the header.
  - Use a descriptive `--name` (e.g. `Kanban Board`); the on-disk filename is derived from it.
  - Confirm the spec is listed by re-running `spec-list`.

## DA.00.3 Configure the app spec

- Look up the available actions FIRST with
  `{{commands.spec-schema.id}} --type powerhouse/app`, then use the
  literal action names it returns. Do not assume the names below are correct
  for any other doc type — each doc-type has its own action vocabulary.
- For `powerhouse/app` specifically, you need to apply (in order):
  - Set the app name (action `SET_APP_NAME`).
  - Register the document types the app surfaces (action `ADD_DOCUMENT_TYPE` per type,
    or `SET_DOCUMENT_TYPES` to replace the whole list).
  - Set drag-and-drop (action `SET_DRAG_AND_DROP_ENABLED`).
  - Confirm with status `"CONFIRMED"` (action `SET_APP_STATUS`).

  Batch all into a single `spec-update --actions '[...]'` call where possible.

- Verify with `{{commands.spec-get.id}} --project <name> --name "<App Name>" --filter $.global`.

## DA.00.4 Verify code generation and the app scaffold

- Run `{{commands.spec-generate.id}} --project <name> --name "<App Name>"` (or wait for the watcher
  to pick up the spec change).
- Verify the app scaffold was created under `<project>/editors/<app-id>/`.
- Confirm `powerhouse.manifest.json` `apps[]` contains an entry with `id` matching the scaffold
  directory name. Note this `id` — it is the `preferredEditor` value for preview drives.
- Explore the scaffold code: `editor.tsx`, `config.ts`, `module.ts`, and `components/`.
