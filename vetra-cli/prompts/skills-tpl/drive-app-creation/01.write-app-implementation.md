## Imports — critical, get these exactly right

Hook names are the #1 failure mode here. Do NOT guess a hook name from what
feels natural — **every hook you use must come from the verified surface below.**
If you can't find one for what you need, the answer is a generated typed hook
(read its file) or a generic reactor-browser hook from this list — never an
invented name.

### Verified API — the COMPLETE surface (copy from here; anything not here does not exist)

These signatures are the real ones (from `@powerhousedao/reactor-browser` and the
codegen templates). A drive app needs **nothing outside this list**. If you reach
for an API that isn't here, you are inventing it — stop and use one of these.

**From `@powerhousedao/reactor-browser`** (drive/document hooks + actions):

| Symbol | Signature | Use |
|--------|-----------|-----|
| `useSelectedDrive()` | `→ [DocumentDriveDocument, dispatch]` (throws if no drive) | the drive the app renders; `driveId = useSelectedDrive()[0].header.id` |
| `useSelectedDriveSafe()` | `→ [drive \| undefined, dispatch \| undefined]` | same, no throw |
| `useNodesInSelectedDrive()` | `→ Node[] \| undefined` | all nodes (files + folders) |
| `useFileNodesInSelectedDrive()` | `→ FileNode[] \| undefined` | file nodes only (pointers, NO doc state) |
| `useDocumentsInSelectedDrive()` | `→ PHDocument[] \| undefined` | **resolved docs WITH `.state`** — list views use this |
| `useDocumentById(id)` | `→ [PHDocument, dispatch]` | load one doc (in-place panel) |
| `useDocumentsByIds(ids)` | `→ (PHDocument \| undefined)[]` | load several |
| `setSelectedNode(node)` | `→ void` | Pattern 1 only (navigates Connect away) |
| `useSetPHAppConfig(editorConfig)` | `→ void` | call once at the top of the app editor |
| `addDocument(driveId, name, documentType, parentFolder?, document?, id?, preferredEditor?)` | `→ Promise<{ id, name, documentType }>` | **create** a doc + add to drive |
| `deleteNode(driveId, nodeId)` | `→ Promise<void>` | **delete** a doc from the drive |

**From `document-models/<model>`** (generated by codegen — read
`document-models/<model>/<v>/hooks.ts` for the exact PascalCase names):

| Symbol | Signature |
|--------|-----------|
| `use<Model>DocumentsInSelectedDrive()` | `→ <Model>Document[] \| undefined` (typed list — prefer this) |
| `use<Model>DocumentById(id)` | `→ [<Model>Document, dispatch] \| [undefined, undefined]` |
| `useSelected<Model>Document()` | `→ [<Model>Document, dispatch]` |
| `use<Model>DocumentsInSelectedFolder()` | `→ <Model>Document[] \| undefined` |
| `actions` | the model's action creators, e.g. `actions.complete({ timestamp })` |

**From `document-model`:** `EditorProps = { children?: ReactNode; className?: string; document?: PHDocument }` — that is the **entire** props object. For a drive app `document` is `undefined`. There is **no** `resolveDocument`, `renderDocument`, `selectDocument`, `documents`, or any other prop.

**Data shapes (read exactly like this):**
- `PHDocument`: `doc.header.{ id, name, documentType, createdAtUtcIso, lastModifiedAtUtcIso }` and `doc.state.global.*` (your model's fields). The id is `doc.header.id`, the name is `doc.header.name` — **NOT** `doc.id` / `doc.name`.
- Drive: `drive.state.global.nodes` is `Node[]` (`FileNode | FolderNode`). `FileNode = { id, name, kind: "file", documentType, parentFolder }`. There is **NO** `drive.state.global.files`, no `documents` map, and a node carries **NO** document state.

**These do NOT exist — never import or call them** (each has been hallucinated; the real replacement is in the tables above):
`useDriveDocuments`, `useDriveDriveDocument`, `useDocumentDriveServer`,
`document-model-libs` (any path), `drive.state.global.files`,
`props.resolveDocument`, `props.renderDocument`, `props.documents`, a "manager"
hook returning `{ documents, createDocument, deleteDocument, selectDocument }`.

### Canonical minimal app editor — start from this, adapt it

This is a complete, working `editor.tsx` for a drive app that lists every
document of one type. It compiles and renders. Copy it, then adapt:

```tsx
import { useSetPHAppConfig } from "@powerhousedao/reactor-browser";
import type { EditorProps } from "document-model";
import { actions, useTaskDocumentsInSelectedDrive } from "document-models/task";
import { useTaskDocumentById } from "document-models/task";
import { editorConfig } from "./config.js";

function TaskRow({ id }: { id: string }) {
  const [doc, dispatch] = useTaskDocumentById(id);   // typed: doc.state.global is the Task state
  if (!doc) return null;
  const done = doc.state.global.done ?? false;
  return (
    <label>
      <input type="checkbox" checked={done}
        onChange={() => dispatch(actions.toggleDone({ done: !done }))} />
      <span>{doc.state.global.title || doc.header.name}</span>
    </label>
  );
}

export default function Editor(_props: EditorProps) {
  useSetPHAppConfig(editorConfig);
  const tasks = useTaskDocumentsInSelectedDrive() ?? [];   // typed PHDocument[] of this model
  return (
    <div>
      <h1>Task Board</h1>
      {tasks.map((d) => <TaskRow key={d.header.id} id={d.header.id} />)}
    </div>
  );
}
```

Substitute your own model name for `Task` everywhere (`useBrandSheetDocumentsInSelectedDrive`,
`actions` from `document-models/brand-sheet`, etc.).

> **STOP — do not read documents off the drive prop. This is the #2 failure mode
> and it renders an EMPTY app with no error.**
>
> - There is **no usable `drive` or `document` prop**. `props.drive` is
>   `undefined`; do not write `props.drive.…`. Get the drive (only if you truly
>   need it) from `useSelectedDrive()`.
> - The drive's `state.global` has **`nodes` only** — an array of FileNode
>   pointers `{ id, name, kind, documentType, parentFolder }`. There is **NO
>   `files` map, NO `documents` map, NO `state` on a node.** Writing
>   `drive.state.global.files[id]`, `node.state.global.*`, or
>   `nodes[id].document` returns `undefined` for every task → both columns show
>   0 → "empty board" bug. The board renders, no console error, just no data —
>   so you will not notice unless you check the counts.
> - **The ONLY way to get documents with their `.state` is a hook that loads
>   them:** `use<Model>DocumentsInSelectedDrive()` (whole list, typed) or
>   `useDocumentsInSelectedDrive()` (generic), and per-document
>   `use<Model>DocumentById(id)`. The canonical editor above already does this —
>   follow its shape exactly; do not "optimize" it into reading the drive prop.
>
> If after wiring the app the preview shows 0 items but the drive was populated,
> you are reading documents off `nodes`/the drive prop. Switch to
> `use<Model>DocumentsInSelectedDrive()`.

### Prefer the generated typed hooks — discover them, don't invent them

Codegen generates a typed hook file per model at
`document-models/<model>/<version>/hooks.ts`, re-exported from
`document-models/<model>`. **Read that file** — it tells you the exact names.
For a model named `Task` you get:

| Generated hook (from `document-models/task`) | Returns |
|----------------------------------------------|---------|
| `useTaskDocumentsInSelectedDrive()` | all Task docs in the drive — `TaskDocument[] \| undefined` |
| `useTaskDocumentsInSelectedFolder()` | all Task docs in the current folder |
| `useTaskDocumentById(id)` | one typed Task doc — `[doc, dispatch]` |
| `useSelectedTaskDocument()` | the currently selected Task doc |

`use<Model>DocumentsInSelectedDrive()` is almost always what you want for a
list view — it is the typed "give me every document of this type" hook. **This
is the hook agents keep trying to invent as `useDriveDocuments` — it exists, it
is just named per-model.** Read `document-models/<model>/<v>/hooks.ts` to confirm
the real names before writing the import.

### Forbidden — these do NOT exist, importing any of them breaks the build

- **`document-model-libs`** (e.g. `document-model-libs/utils`) — entire package
  removed in the reactor-browser refactor. Any import fails Vite with "Failed to
  resolve import / Failed to fetch dynamically imported module" and renders
  "Something went wrong".
- **`useDriveDocuments`** — invented, and the single most common failure here.
  There is NO all-in-one "drive documents manager" hook. Do not import it, and do
  **not** expect a hook to hand you `{ documents, createDocument, deleteDocument,
  selectDocument }` — those returns are invented too. Get the list from
  `use<Model>DocumentsInSelectedDrive()` (typed) or `useDocumentsInSelectedDrive()`
  (generic); create/delete via the standalone functions in the CRUD section below.
- **`useDocumentDriveServer`** — invented/removed. Get the drive with
  `useSelectedDrive()`.
- Any `use<Something>` you have not seen in `document-models/<model>/<v>/hooks.ts`
  or in the allow-list below. When unsure, grep the package, do not guess.

### The only valid import sources in an app `editor.tsx`

| Import from | What you get |
|-------------|--------------|
| `document-models/<model>` | **typed** hooks (`use<Model>DocumentsInSelectedDrive`, `use<Model>DocumentById`, `useSelected<Model>Document`), that model's `actions`, and typed `State` — PREFER THESE |
| `@powerhousedao/reactor-browser` | generic untyped drive/document hooks (allow-list below) + `useSetPHAppConfig`, `setSelectedNode`, `addDocument` |
| `document-model` | `EditorProps` (the component's props type) |
| `@powerhousedao/shared/document-drive` | `FileNode`, `FolderNode` types (only if you read `drive.state.global.nodes` directly) |
| `./config.js`, `./<YourComponent>.js` | the generated `editorConfig` and your own components |

**Generic reactor-browser hooks that actually exist** (verified exports — use a
typed `document-models/<model>` hook instead where one fits):
`useSelectedDrive`, `useSelectedDriveSafe`, `useDocumentsInSelectedDrive`,
`useDocumentTypesInSelectedDrive`, `useNodesInSelectedDrive`,
`useFileNodesInSelectedDrive`, `useDocumentById`, `useDocuments`,
`useDocumentsByIds`, `useSelectedDocument`, `useDriveById`, `setSelectedNode`,
`addDocument`, `useSetPHAppConfig`.

When in doubt about the exact hook, **read `vetra-app/editors/vetra-studio/`** —
it is the reference in-place drive app (selection state, URL persistence, typed

### Create / delete documents (CRUD) — use these standalone functions

Create and delete are **standalone functions** from `@powerhousedao/reactor-browser`,
NOT methods on a hook. You need the drive id from `useSelectedDrive()`:

```tsx
import { useSelectedDrive, addDocument, deleteNode } from "@powerhousedao/reactor-browser";

const [drive] = useSelectedDrive();
const driveId = drive?.header.id;

// create a new document of your model's type (returns { id, name, documentType })
const created = await addDocument(driveId, "New Habit", "powerhouse/habit");
setSelectedId(created.id);            // e.g. open it in your panel

// delete a document (a drive node) by id
await deleteNode(driveId, habitId);
```

- `addDocument(driveId, name, documentType)` — creates the doc AND adds it to the
  drive. The "+ New" button calls this.
- `deleteNode(driveId, nodeId)` — removes the doc from the drive. The per-row
  "Delete" button calls this. (It's `deleteNode`, not `deleteDocument`.)
- The list (`use<Model>DocumentsInSelectedDrive()`) is reactive — it updates on
  its own after create/delete; do not maintain a parallel array.

## Two rendering patterns

A drive app decides what happens when the user opens a document inside the drive.
There are two patterns — **choose pattern 2 (in-place) by default**; it produces
better UX for real apps.

### Pattern 1: Connect-navigation (generic scaffold)

The app calls `setSelectedNode(node)` from `@powerhousedao/reactor-browser`.
Connect **navigates away** — it replaces the whole drive view with that
document's editor. The generated scaffold uses this pattern: Connect passes the
selected document's editor in as `props.children`, and the app renders
`children` when a node is selected.

```tsx
import { setSelectedNode } from "@powerhousedao/reactor-browser";
// When the user clicks a document:
setSelectedNode(node);
// Connect navigates to the document's editor, replacing the drive view.
// props.children contains the child editor when a node is selected.
```

Use this when the app is a simple file browser and navigating away is acceptable.

### Pattern 2: In-place / custom (recommended — what Vetra Studio does)

The app keeps an **internal selected-document state** and renders the document's
editor **inside its own layout** — it does **not** call `setSelectedNode`.
This is how you build a "real app" experience where opening a document doesn't
blow away your shell.

> **CRITICAL — how to get the drive and read document state (do NOT get this wrong):**
> - An app/drive editor component does **NOT receive a usable `document` prop**.
>   Do **not** read `props.document` — for a drive app it is `undefined`. Get the
>   live drive with `useSelectedDrive()` → `[driveDoc, dispatch]`.
> - `driveDoc.state.global.nodes` are **FileNodes** =
>   `{ id, name, kind, documentType, parentFolder }`. They carry **NO document
>   state** — you cannot read `node.state.global.*` (e.g. `done`, `title`). A node
>   is a pointer, not the document.
> - To read a document's fields, **LOAD it**: `useDocumentById(id)` or the typed
>   `use<Model>DocumentById(id)` from `document-models/<model>` → `[doc, dispatch]`,
>   then read `doc.state.global.*`. To list+read every document of a type at once:
>   `useDocumentsInSelectedDrive()` → `PHDocument[]`, filter by
>   `d.header.documentType`, read `d.state.global.*`.
> - **Do NOT render `props.children` for your in-place panel.** `children` is only
>   populated in Pattern 1 (after `setSelectedNode`). In Pattern 2 you own the
>   selection (`useState` of the selected id) so `children` is empty — rendering it
>   gives a blank panel. Build the panel yourself: load the selected doc with
>   `use<Model>DocumentById(selectedId)` and render its fields/editor. (Reading
>   `doc.header.id` / `doc.header.name`, not `doc.id` / `doc.name`.)

```tsx
import { useSelectedDrive } from "@powerhousedao/reactor-browser";
import { useTodoListDocumentById } from "document-models/todo-list"; // typed hook is per-model
import type { FileNode } from "@powerhousedao/shared/document-drive";

export default function Editor() {            // no `document` prop — use the hook
  const [drive] = useSelectedDrive();         // the LIVE drive document
  const files = drive.state.global.nodes.filter(
    (n): n is FileNode => n.kind === "file" && n.documentType === "powerhouse/todo-list",
  );
  const [selectedId, setSelectedId] = useDocSelection();  // ?doc=<id> in the URL
  const [selectedDoc, selectedDispatch] = useTodoListDocumentById(selectedId); // has .state

  return (
    <div className="flex h-full">
      <Sidebar files={files} onSelect={setSelectedId} />
      <main>
        {selectedDoc
          ? <TodoListEditor document={selectedDoc} dispatch={selectedDispatch} />
          : <DashboardView files={files} />}
      </main>
    </div>
  );
}
```

Persist the selection in a **URL query param** (`?doc=<id>`) so refresh restores
it. There is no `useQueryParam` helper — write a tiny hook over `URLSearchParams`
+ `history.replaceState` + a `popstate` listener. Vetra Studio's `VetraStudio.tsx`
does exactly this for `?session=` — copy that pattern.

To render the correct editor for a document type, switch on `documentType`:

```tsx
function EditorForType({ doc, dispatch }) {
  switch (doc.documentType) {
    case "powerhouse/todo-list":
      return <TodoListEditor document={doc} dispatch={dispatch} />;
    case "powerhouse/note":
      return <NoteEditor document={doc} dispatch={dispatch} />;
    default:
      return <div>No editor for {doc.documentType}</div>;
  }
}
```

> Where a typed editor needs a typed document, prefer the model's generated typed
> hook (e.g. `useBrandSheetDocumentById(id)` from `document-models/brand-sheet`)
> over the generic `useDocumentById`, which returns an untyped `PHDocument`. This
> is what Vetra Studio's `DocumentHost` does.

## Drive introspection API

All from `@powerhousedao/reactor-browser`:

| Hook / function | Use |
|-----------------|-----|
| `useSelectedDrive()` → `[driveDoc, dispatch]` | The drive the app renders |
| `useNodesInSelectedDrive()` | All nodes (files + folders) |
| `useFileNodesInSelectedDrive()` | Files only |
| `useDocumentsInSelectedDrive()` | Documents (resolved, with state) |
| `useDocumentById(id)` → `[doc, dispatch]` | Load a specific doc for in-place rendering |
| `useDocumentsInSelectedDrive()` → `PHDocument[]` | Every resolved doc in the drive (generic; prefer `use<Model>DocumentsInSelectedDrive`) |
| `setSelectedNode(node)` | Navigate Connect to a node (pattern 1) |
| `addDocument(driveId, name, type, parentFolder?, doc?, id?, preferredEditor?)` | Create a doc |

Get the drive document from `useSelectedDrive()` (type `DocumentDriveDocument`),
**not** from `props.document` — a drive app receives no usable `document` prop.
The drive's `state.global.nodes` array contains all top-level entries: filter by
`kind === "file"` for documents, by `documentType` for specific types. Remember
nodes are pointers with no document state — load the document (typed
`use<Model>DocumentById` / generic `useDocumentById`) to read its fields.

## DA.01.2 Implement the app UI

**Choose the rendering pattern** (see above). Default to pattern 2 (in-place).

**Design styles:** unless otherwise specified, stick to a sober, generic
SaaS-style design for business use cases: white background, rounded corners,
grey accent backgrounds and borders, soft edges, subtle use of shadows, and
color usage mostly for labels, chips, and warnings/errors.

**Structure the layout:**
- A drive app typically has a main content area and optionally a sidebar.
- Use the drive's nodes to populate the view (lists, cards, table rows, etc.).
- For in-place rendering, maintain a selected-document state and render the
  editor inline when a document is selected.
- Persist selection in a URL query param so the state survives refresh.

**Implement interactions** (see the CRUD section above for the exact signatures):
- Creating: `addDocument(driveId, name, type)` from `@powerhousedao/reactor-browser`
  (`driveId` = `useSelectedDrive()[0].header.id`).
- Deleting: `deleteNode(driveId, nodeId)` from `@powerhousedao/reactor-browser`.
- Navigating between documents: update the internal selection state (pattern 2)
  or call `setSelectedNode` (pattern 1) — do not mix them (no `children` in p2).

## DA.01.3 Resolve outstanding issues

- **GATE — run `{{commands.reactor-project-check.id}} --project <name>` and make it
  pass BEFORE you preview (DA.02).** This typechecks the `editors/`+`apps/` trees
  and is what catches invented imports/hooks (e.g. `useDriveDocuments`,
  `useDocumentDriveServer`) and wrong field access (`doc.id` vs `doc.header.id`) —
  exactly the bugs that otherwise render "Something went wrong" in the preview with
  no other signal. Fix every error it reports, then re-run it until clean.
  - This is the same check the document-model skill uses after editing reducers.
  - `{{commands.spec-preview-show.id}}` **also runs this check and refuses to
    return a preview URL while type errors remain** — so a broken app cannot reach
    the BUILD pane. Don't try to work around it; fix the errors (they are real).
  - **NEVER** use `any` or strong type casts to silence an error. If a hook/field
    doesn't type-check, you used the wrong name — fix the name (consult the
    Verified API table above), don't cast. `{{commands.spec-preview-show.id}}`
    **also blocks on `any`/unsafe-access lint errors** (`as any` is not an escape
    hatch — it produces a compiling-but-broken app, so the gate rejects it too).
- Run `pnpm lint:fix` to detect linter issues and auto-fix where possible.
- Run `pnpm test` to ensure that the unit tests are still passing.
