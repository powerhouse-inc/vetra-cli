# DA.02 Preview the drive app

For this scenario, you will create a **preview drive** bound to the app (not a
preview document — an app is a drive-level view), populate it with sample
documents, and show it in the BUILD pane.

> **Precondition — the project must type-check first (DA.01.3).** Run
> `{{commands.reactor-project-check.id}} --project <name>` and fix every error.
> `{{commands.spec-preview-show.id}}` enforces this: it re-runs the typecheck and
> **returns "Preview blocked" with the errors instead of a URL** while any remain
> (a non-compiling app would otherwise render "Something went wrong" with no other
> signal). Fix the reported names/fields against the Verified API table in DA.01;
> do not cast them away.

## DA.02.1 Create the preview drive

Use `{{commands.spec-preview-create-drive.id}}` to create a new drive configured
to use the app as its preferred editor:

```
spec-preview-create-drive --project <name> --app "<App Name>"
```

This creates a top-level drive with `preferredEditor` set to the app's editor
`config.id` (read from `powerhouse.manifest.json` `apps[]`). The command returns
the new drive's `id` — you need it for the next steps.

If a preview drive for this app already exists, the command reuses it
(idempotent by the app it's bound to — the `preferredEditor` — not by drive
name, so a different `--name` still reuses the same app's drive).

## DA.02.2 Populate the preview drive with sample documents

**`--drive <driveId>` is REQUIRED on every populate call.** Pass the exact
`driveId` returned by `{{commands.spec-preview-create-drive.id}}` to BOTH
`{{commands.spec-preview-create.id}}` AND `{{commands.spec-preview-update.id}}`.
If you omit `--drive`, the document goes to the project's *default* preview drive
and the **app drive stays empty** — the preview then shows an empty app. Do NOT
use `{{commands.spec-preview-create.id}} --type powerhouse/document-drive` to make
the drive; the drive already exists (you made it with
`{{commands.spec-preview-create-drive.id}}`). Use the app's *document* types here
(e.g. `powerhouse/<your-model>`), never the drive type.

Create the documents the app surfaces:

```
spec-preview-create --project <name> --drive <driveId> --type powerhouse/<your-model> --name "<Sample Name>"
```

Consider adding a small/medium/large example of each type, and documents in
various states if the model has status workflows.

Then fill them with sample data (again **with `--drive`**):

```
spec-preview-update --project <name> --drive <driveId> --name "<Sample Name>" --actions '[...]'
```

## DA.02.3 Show the app in the BUILD pane

Use `{{commands.spec-preview-show.id}}` with **both `--drive` and `--app`**:

```
spec-preview-show --project <name> --drive <driveId> --app "<App Name>"
```

`--app` is REQUIRED here. Populating the drive (DA.02.2) **wipes the drive's
`preferredEditor` binding** (adding a document re-materializes the drive header
without it), so `spec-preview-show --app` re-asserts the binding as the final
step before the user views the preview. Without `--app`, the drive opens as the
generic file explorer, not your app. This returns a drive-root URL
(`/d/<driveId>?embed=1&driveUrl=…`) that renders the app component in Connect.

**Gate:** the BUILD pane renders the running app with sample content. If it shows
the generic file explorer: you forgot `--app` (binding not re-asserted), or the
app's `id` doesn't match `powerhouse.manifest.json` `apps[]` — re-check and
re-run with `--app`.

## DA.02.4 Iterate on the app UI

After previewing, the user may request changes to the app's UI or behavior.
Edit `editor.tsx` and any custom component files, then verify with
`{{commands.spec-preview-show.id}}` again. No reactor restart needed — Vite HMR
picks up changes automatically.
