# Vetra Studio Teams (Project 6) Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** A Studio becomes the place where a Renown organisation builds and runs its tools together, provably: org-owned Studios with roles, one open change per person with a board and agent-combined versions, anchored comments with @agent, signed four-eyes review before live, presence, a team brain, an org library, a shared budget, notifications, triage, time-boxed guests and a signed audit export.

**Architecture:** Identity stays Renown; the org is the existing `powerhouse/renown-organization` document, read through the Renown `orgMembership` query. Per-Studio facts (reviewers, overrides, review setting, guests, member limits) live in a new `vetra/studio-team` document in the Studio drive. Authority never comes from reducer state of browser-writable documents: the Studio agent process verifies each security-relevant operation's v2 signature and its signer's role once, records the verdict in a trust ledger, and acts only on accepted operations. The agent signs its own work with the requesting member's delegation to the Studio's app key. The cloud (vetra-cloud-package) adds org licences, org claims, a stable org publisher identity, an org budget pool, notifications and the org handbook. Concurrent changes get one git branch each and share the workspace through a build lane.

**Tech Stack:** TypeScript; React 19 + Tailwind v4 Connect editors (vitest 4, happy-dom) in `vetra-app`; vetra-cli on ph-clint + Mastra (jest ESM); Powerhouse document models via `ph-cli generate`; `@renown/sdk` (bearer, delegation credentials) and powerhouse `action-signature` (v2); vetra-cloud-package subgraphs/processors (vitest, Kysely/Postgres); Verdaccio registry plugin (powerhouse `packages/registry`); Playwright staging harness (node ESM).

**Spec:** `docs/superpowers/specs/2026-10-21-teams-design.md` (copied from `spec/iterate-design` commit `504699d`: approved, Q1 decided — org licence). Builds on Projects 2+3, P4 (`docs/superpowers/plans/2026-10-21-iterate-design.md`) and P5 (`docs/superpowers/plans/2026-10-21-first-minutes.md`).

## Review Focus

1. **A member removed or downgraded mid-flight** — their Studio-bound bearer is refused within `MEMBERSHIP_TTL_MS = 60_000`, their drive access is withdrawn on the next sync, their open change pauses with `Paused — <name> no longer has access`, and the agent never signs another operation with their delegation. Tests: Task 1.7 `a removed member is refused after the cache expires`, Task 1.11 `revoked member's change pauses and nothing more is signed for them`.
2. **An approval that isn't provable** — unsigned, signed by a key the approver never delegated, signed by a non-Reviewer, by the requester of an included change, for another sha, or replayed from another Studio's document — is rejected and the launch refuses. Test: Task 4.1 `every unprovable approval is rejected` (table test, one row per case).
3. **The candidate changes after approval** — any commit after the approved sha, a different package version, or a change added to the combine voids the approval and the board shows `Needs review again`. Test: Task 4.1 `a commit after approval voids it`.
4. **An org-private product reached from outside** — tarball, packument, CDN file and search for an org-private package by anonymous, a non-member and a member of another org all answer 404 (not 403) with `Cache-Control: private, no-store`. Test: Task 8.1 `org-private package is invisible outside the org`.
5. **Renown or the cloud is down** — membership lookups that fail grant nothing new (fail closed), cached verdicts stay until TTL, the agent keeps working on changes it already accepted, and the UI shows the access message instead of a blank Studio. Test: Task 1.7 `orgs service down: cached member keeps access until TTL, unknown member refused`.

## Plan rulings (copied into the ledger at execution start)

- P6-1 **Membership** = Renown org role (via `orgMembership(orgId, address)`, ACTIVE only) mapped OWNER/ADMIN → Owner, PUBLISHER with publisher capability for the Studio's App → Maker, PUBLISHER without it and MEMBER → Viewer; plus the per-Studio `vetra/studio-team` document: `reviewers` (Reviewer is a flag on top of the base role), `roleOverrides` (may only **lower** Maker → Viewer; raising happens in Renown so cloud operators and Studio roles never disagree), guests, member limits, review setting. Personal Studios: `ADMINS` → Owner, nobody else. No second org concept.
- P6-2 **Authority from verified operations:** security decisions (team settings, approvals, change ownership, guest rights, triage assignment, member limits, launch/rollback requests in org Studios) read only operations accepted by the trust ledger (`team/trust.ts`): v2 signature valid for the document, the signer's (address, app key) delegation confirmed with Renown, the signer's role sufficient **at the moment the Studio first saw the operation**. Verdicts are stored once (`.ph/vetra/team/trust.json`) and never recomputed. Reducer state is display only. Unsigned or unverifiable security-relevant operations are ignored and shown in the audit as `unsigned`.
- P6-3 **Writes by role:** Owners and Makers write the Studio drive directly (as today, Connect signs). Viewers and guests get read-only drive access (guests: no drive access, see P6-12); their comments/steers go through `POST /team/relay` as actions **signed in their own browser**; the relay checks the capability and appends the signed action unchanged.
- P6-4 **Agent identity:** one app key per Studio (`.ph/.keypair.json`), one stored delegation per member (`.ph/vetra/team/delegations/<address>.json`, Renown storage per address on the same key). The agent signs everything it does for a change with the change owner's delegation (v2, `user.address` = member). "Allow" is per member (Projects 2+3 Task 2.8 flow, now accepting any Maker or Owner). A member without a stored delegation is asked on their first agent request.
- P6-5 **Publishing identity:** org Studios publish to the registry as the **org publisher**: an EOA the cloud creates per org licence (key encrypted like `anthropic_key_ciphertext`), which delegates to each org Studio's app key on request (`orgPublisherCredential`, Studio-agent bound). Package ownership in the registry then never depends on a person; people are recorded in the version, approval and audit. Cloud launch calls still use the launch requester's delegation (an org operator).
- P6-6 **Org licence:** the holder is the org (`org_id` on the grant); issued through the existing issuers (invite code redeemed *for an org* by its Owner; publisher grant to an org); `ACHRA_SUBSCRIPTION` stays the reserved seam. Org claims and moves require an active org licence; the org budget pool hangs off it; members need no licence. Moving a personal Studio adds its remaining budget (limit − usage) to the pool.
- P6-7 **Org pod config:** org Studio pods get `VETRA_STUDIO_ORG_ID`, `VETRA_RENOWN_ORGS_URL`; reactor `ADMINS` holds no person (empty, or the result of Task 1.10's spike if the reactor needs one); human access to the Studio drive is the pod-synced document grants of Task 1.10.
- P6-8 **Build lane:** one change at a time uses the workspace (a "lane"); each change has branch `change/<id>` from the live tag; the lane switches between agent turns (WIP commit on the change branch, checkout the next); others wait (`Waiting to build`). A second lane (worktree + P4's second preview service) is enabled only if Task 2.3's measurement shows two builds fit (`SECOND_LANE_MIN_FREE_MB`, recorded); otherwise `CHANGE_LANES = 1` is the ruling and the spec target is reported as not met with numbers.
- P6-9 **What is approved** is a candidate `{sha, packages[]}` built by combining ready changes in board order on `combine/<id>`; launch publishes exactly that sha; any later commit or package version difference voids it.
- P6-10 **Four-eyes:** the approver must be a Reviewer and must not own any change included in the candidate nor have requested the review. Owners are not Reviewers unless listed. Turning "Going live needs a review" off is an Owner-signed `studio-team` operation and an audit event.
- P6-11 **Presence** runs in the Studio pod: authenticated SSE down (`?token=` = a Studio-bound bearer, verified like headers), `POST /team/presence` up (≤ 10/s per person), memory only, entries expire after 30 s.
- P6-12 **Guests** use a guest page (`/guest/<inviteId>`) that reads their change through routes, never the drive; sign-in with Renown like the Studio; their actions are browser-signed and relayed; access ends at `expiresAt` or on revoke (checked on every request).
- P6-13 **Team brain** is a cloud document `vetra/org-handbook` (one per org, cloud switchboard, v2-required), editable by org OWNER/ADMIN (synced editor list, like the environment's `orgOperators`), readable by members and the org's Studio agents.
- P6-14 **Notifications** are cloud-side: org webhooks (Slack, Microsoft Teams) stored encrypted and never returned; email through an SMTP seam (`VETRA_SMTP_URL`; unset → email shows `Email isn't set up yet`); in-Studio inbox in the pod; daily digest from the cloud's event table at 08:00 in each person's time zone (default Europe/Berlin).
- P6-15 **Org-private packages** are a per-package registry flag (`registry_package_access(package_name, org_id)`), names unchanged (`@vetra-apps/<slug>`); read access by Renown org membership; the registry change ships to a local/dev registry only (registry.dev.vetra.io if its deploy is ours to do, else a harness-run registry) — registry.vetra.io's rollout is Frank's call.
- P6-16 **Audit export** is built from accepted and rejected operations of the product, team and thread documents, plus environment document operations (cloud) and org audit log (Renown); the signed JSON carries each operation's signature tuple and the delegation credential for each (address, app key) so it verifies offline with `vetra audit verify <file>`.
